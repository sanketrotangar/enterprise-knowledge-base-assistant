## 1. Project Overview

### Problem Statement

Enterprise employees repeatedly struggle to find internal knowledge scattered across PDFs, Google Docs, and Notion. Information exists but is inaccessible — a classic "know what exists but can't find it" problem.

### Solution

Build an **Enterprise Knowledge Assistant** — a RAG (Retrieval-Augmented Generation) system that:

- **Ingests** uploaded PDFs/documents
- **Chunks + embeds** document content into vector representations
- **Searches** using hybrid search (BM25 sparse + vector dense retrieval)
- **Reranks** results for precision
- **Enforces access control** based on roles (HR, Engineering, hierarchy levels)
- **Cites sources** in responses
- **Collects feedback** to improve over time

### Core User Flow

```
Employee asks: "Where is the leave policy?"
    → System searches indexed documents via hybrid search
    → Cross-encoder reranks top-k candidates
    → LLM generates answer with source citations
    → User sees answer + can rate usefulness
```

### 2.2 Component Responsibilities

| Component | Responsibility | Technology |
|-----------|---------------|------------|
| **API Server** | HTTP endpoints, auth, RBAC, request routing | FastAPI + Uvicorn |
| **Metadata DB** | Users, documents, roles, permissions, audit, feedback | PostgreSQL + SQLAlchemy |
| **Vector Store** | Document embeddings, hybrid search (dense + sparse) | Qdrant |
| **Cache Layer** | Query result caching, rate limiting, session management | Redis |
| **Background Worker** | Async document processing pipeline | Celery + Redis broker |
| **Embedding Model** | Text-to-vector conversion | sentence-transformers |
| **Reranker** | Precision reranking of search results | cross-encoder/ms-marco |
| **File Storage** | Uploaded document storage | Local disk (MVP) → S3 (production) |

## 3. Database Schema Design

### 3.1 PostgreSQL Schema

```sql
-- ============================================================
-- ORGANIZATIONS
-- ============================================================
CREATE TABLE organizations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            VARCHAR(255) NOT NULL,
    slug            VARCHAR(100) UNIQUE NOT NULL,
    settings        JSONB DEFAULT '{}',
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

-- ============================================================
-- USERS
-- ============================================================
CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id          UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    email           VARCHAR(255) NOT NULL,
    name            VARCHAR(255) NOT NULL,
    role            VARCHAR(50) NOT NULL DEFAULT 'employee',
                    -- 'admin', 'manager', 'employee', 'intern'
    department      VARCHAR(100),  -- 'hr', 'engineering', 'finance', 'general'
    manager_id      UUID REFERENCES users(id),
    password_hash   VARCHAR(255) NOT NULL,
    is_active       BOOLEAN DEFAULT true,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(org_id, email)
);

-- Index for RBAC lookups
CREATE INDEX idx_users_org_role ON users(org_id, role);
CREATE INDEX idx_users_manager ON users(manager_id);

-- ============================================================
-- DOCUMENTS
-- ============================================================
CREATE TABLE documents (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id          UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    title           VARCHAR(500) NOT NULL,
    source_type     VARCHAR(50) NOT NULL DEFAULT 'upload',
                    -- 'upload', 'google_drive', 'notion', 'url'
    storage_path    VARCHAR(1000) NOT NULL,
    file_size_bytes BIGINT,
    mime_type       VARCHAR(100),
    uploaded_by     UUID NOT NULL REFERENCES users(id),
    sensitivity     VARCHAR(50) DEFAULT 'internal',
                    -- 'public', 'internal', 'confidential', 'restricted'
    role_access     VARCHAR(50)[] DEFAULT '{}',
                    -- ['hr', 'engineering'] — empty = all roles
    status          VARCHAR(50) DEFAULT 'uploaded',
                    -- 'uploaded', 'processing', 'indexed', 'failed'
    chunk_count     INTEGER DEFAULT 0,
    metadata        JSONB DEFAULT '{}',  -- extra info, tags, etc.
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_documents_org ON documents(org_id);
CREATE INDEX idx_documents_status ON documents(status);
CREATE INDEX idx_documents_sensitivity ON documents(sensitivity);

-- ============================================================
-- DOCUMENT CHUNKS (reference to Qdrant points)
-- ============================================================
CREATE TABLE document_chunks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id     UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    qdrant_point_id UUID UNIQUE NOT NULL,  -- ID in Qdrant
    chunk_index     INTEGER NOT NULL,
    content_preview TEXT,  -- first 200 chars for debugging
    token_count     INTEGER,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_chunks_document ON document_chunks(document_id);

-- ============================================================
-- SEARCH QUERIES (for analytics and feedback)
-- ============================================================
CREATE TABLE search_queries (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(id),
    org_id          UUID NOT NULL REFERENCES organizations(id),
    query_text      TEXT NOT NULL,
    results_count   INTEGER DEFAULT 0,
    response_time_ms INTEGER,
    answer_text     TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_queries_user ON search_queries(user_id);
CREATE INDEX idx_queries_org_time ON search_queries(org_id, created_at DESC);

-- ============================================================
-- QUERY RESULT CITATIONS
-- ============================================================
CREATE TABLE query_citations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    query_id        UUID NOT NULL REFERENCES search_queries(id) ON DELETE CASCADE,
    document_id     UUID NOT NULL REFERENCES documents(id),
    chunk_id        UUID REFERENCES document_chunks(id),
    relevance_score FLOAT,  -- reranker score
    position        INTEGER NOT NULL,  -- rank in results
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_citations_query ON query_citations(query_id);

-- ============================================================
-- FEEDBACK
-- ============================================================
CREATE TABLE feedback (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    query_id        UUID NOT NULL REFERENCES search_queries(id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(id),
    rating          VARCHAR(20) NOT NULL,  -- 'useful', 'not_useful', 'partial'
    comment         TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_feedback_query ON feedback(query_id);
CREATE UNIQUE INDEX idx_feedback_unique_per_user ON feedback(query_id, user_id);

-- ============================================================
-- AUDIT LOG (for compliance and debugging)
-- ============================================================
CREATE TABLE audit_logs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id          UUID NOT NULL,
    user_id         UUID,
    action          VARCHAR(100) NOT NULL,  -- 'document.upload', 'search.query', 'user.login'
    resource_type   VARCHAR(50),
    resource_id     UUID,
    details         JSONB DEFAULT '{}',
    ip_address      INET,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_audit_org_time ON audit_logs(org_id, created_at DESC);
CREATE INDEX idx_audit_user ON audit_logs(user_id);
```

### 3.2 Qdrant Collection Schema

```
Collection: "enterprise_embeddings"

Vector:
  - name: "dense"
    size: 768  (or 384 depending on model)
    distance: Cosine

Sparse Vector:
  - name: "sparse" (BM25 via Qdrant's built-in sparse vectors)

Payload (per point):
{
  "document_id": UUID,
  "chunk_id": UUID,
  "org_id": UUID,
  "chunk_index": int,
  "content": string,         // full chunk text
  "sensitivity": string,     // 'public' | 'internal' | 'confidential' | 'restricted'
  "role_access": [string],   // ['hr', 'engineering'] or []
  "source_type": string,     // 'upload', 'google_drive', etc.
  "title": string,           // document title
  "uploaded_at": datetime
}

Indexing:
  - Payload index on "org_id" (for tenant isolation)
  - Payload index on "sensitivity" (for access filtering)
  - Payload index on "role_access" (for role filtering)
```

## 4. Assumptions

### 4.1 Product Assumptions

| # | Assumption | Risk if Wrong | Validation Needed |
|---|-----------|---------------|-------------------|
| 1 | **Documents are primarily PDFs** — 80%+ of uploads will be PDF format | Backend parsing won't handle Word/PowerPoint well | Ask customer about document mix |
| 2 | **Single-tenant per deployment** — Each org gets its own deployment OR strong tenant isolation in shared deployment | Data leakage between orgs | Confirm with stakeholder |
| 3 | **English-only content** — No multilingual support needed initially | Limited utility for global companies | Confirm with stakeholder |
| 4 | **Users authenticate via existing IdP** (SSO/OAuth) or simple email/password | Auth integration complexity varies wildly | Confirm authentication requirements |
| 5 | **Documents are small to medium** (1-100 pages) — No 1000+ page manuals | Chunking strategy and processing time differ | Confirm typical document sizes |
| 6 | **Query volume: <100 concurrent users** — Intranet tool, not public-facing | Infrastructure sizing assumptions | Confirm expected user base |
| 7 | **No real-time document sync** — Manual upload is sufficient | Misses constantly-updating docs like Notion | Confirm if auto-sync is needed |
| 8 | **Feedback is simple thumbs up/down** — Not detailed surveys | Less useful training signal | Confirm feedback requirements |

### 4.2 Technical Assumptions

| # | Assumption | Risk if Wrong | Mitigation |
|---|-----------|---------------|------------|
| 1 | **sentence-transformers runs on CPU** is acceptable for <1000 docs | Slow embedding for large corpora | GPU available for production |
| 2 | **Qdrant single-node** is sufficient for initial scale | Need distributed Qdrant early | Design for easy sharding |
| 3 | **Redis single-node** for caching/queuing | Cache misses degrade performance | Redis Sentinel for HA |
| 4 | **Local filesystem** for MVP document storage | Not production-ready, no HA | Upgrade to S3/MinIO |
| 5 | **No streaming responses** — Synchronous response generation | Users wait for full response | Add SSE streaming later |
| 6 | **Cross-encoder reranking adds acceptable latency** (~200-500ms) | Response feels slow | Make reranking optional, cache |

### 4.3 Security Assumptions

| # | Assumption | Risk if Wrong |
|---|-----------|---------------|
| 1 | **Internal tool only** — Not exposed to public internet | Needs WAF, DDoS protection |
| 2 | **No PII in documents** — Only policy/procedure docs | GDPR/CCPA compliance required |
| 3 | **Basic audit logging** — Not SOC2/HIPAA compliant initially | Compliance certification needed |
| 4 | **Password hashing** is sufficient — No MFA needed initially | Security team may require MFA |

## 5. Tradeoffs Considered

### 5.1 Search Strategy Tradeoffs

| Decision | Option A | Option B | **Chosen** | Rationale |
|----------|----------|----------|------------|-----------|
| **Search type** | BM25 only | Vector only | **Hybrid (BM25 + Vector)** | Keyword search misses semantics ("PTO" vs "paid time off"), semantic search misses exact terms ("policy-v2.3"). Hybrid covers both. |
| **Fusion method** | Reciprocal Rank Fusion (RRF) | Weighted sum | **RRF** | Parameter-free, works well across query types, no need to tune weights. |
| **Reranking** | None (rely on fusion) | Cross-encoder reranker | **Cross-encoder** | Initial retrieval is broad; reranker dramatically improves precision for the top-5 shown to user. Cost: +200-500ms latency. |
| **Embedding model** | OpenAI embeddings API | sentence-transformers (local) | **sentence-transformers** | No API dependency, no data leaves the network (critical for enterprise docs), free, good quality. |

### 5.2 Architecture Tradeoffs

| Decision | Option A | Option B | **Chosen** | Rationale |
|----------|----------|----------|------------|-----------|
| **Document storage** | PostgreSQL (bytea) | S3/MinIO | **Local disk → S3** | Start simple, migrate when needed. PostgreSQL bloats with binary data. |
| **Async processing** | In-process (asyncio) | Background worker (Celery) | **Celery** | Decouples processing, retries on failure, scales independently. Overhead is justified for reliability. |
| **LLM for generation** | OpenAI API | Open-source LLM (local) | **OpenAI API (configurable)** | Best quality out of the box. Design interface to swap later if needed (Ollama, etc.). |
| **Session management** | JWT (stateless) | Server-side sessions (Redis) | **JWT + Redis** | JWT for API auth (stateless, scalable), Redis for rate limiting and cache. |
| **Caching strategy** | Cache everything | Cache nothing | **Cache search results** | Same query is common in enterprises ("leave policy" asked 10x/day). TTL-based with invalidation on document update. |

### 5.3 Schema Design Tradeoffs

| Decision | Option A | Option B | **Chosen** | Rationale |
|----------|----------|----------|------------|-----------|
| **Chunking strategy** | Fixed-size (512 tokens) | Semantic (paragraph/section) | **Fixed-size with overlap** | Deterministic, no LLM dependency, predictable embeddings. Semantic chunking is better quality but harder to implement reliably. |
| **Role access model** | RBAC (roles only) | ABAC (attributes like department, level) | **RBAC with sensitivity levels** | Simpler to implement and reason about. ABAC adds complexity. Can extend later. |
| **Feedback storage** | Same table as queries | Separate feedback table | **Separate table** | Allows many-to-one feedback per query, cleaner analytics, separate retention policies. |

## 6. Scalability Analysis

### 6.1 Current Design Capacity

| Dimension | MVP Capacity | Bottleneck |
|-----------|-------------|------------|
| **Concurrent users** | ~50-100 | Redis connection pool, PostgreSQL connections |
| **Documents per org** | ~10,000 | Qdrant collection size, embedding computation time |
| **Total chunks** | ~1M (10K docs × 100 chunks avg) | Qdrant memory, vector search latency |
| **Queries per second** | ~10-20 QPS | Embedding inference (CPU), reranking latency |
| **Document upload throughput** | ~10 concurrent uploads | Filesystem I/O, Celery worker concurrency |

### 6.2 Scale-Up Strategies

```
Phase 1: MVP (1 org, <100 users)
├── Single FastAPI instance
├── Single PostgreSQL
├── Single Qdrant node
├── Single Redis
├── 2-4 Celery workers
└── Local filesystem

Phase 2: Growth (10-50 orgs, <1000 users each)
├── FastAPI behind Nginx/load balancer
├── PostgreSQL with read replicas
├── Qdrant with replication factor 2
├── Redis Sentinel (HA)
├── 4-8 Celery workers
└── S3/MinIO for document storage

Phase 3: Enterprise (100+ orgs, 10000+ users)
├── Multiple FastAPI instances (Kubernetes)
├── PostgreSQL with connection pooling (PgBouncer)
├── Distributed Qdrant cluster
├── Redis Cluster
├── Celery with autoscaling
├── CDN for static assets
├── GPU instances for embedding/reranking
└── Multi-region deployment
```

### 6.3 Scaling Considerations

| Concern | Strategy |
|---------|----------|
| **Vector search latency at scale** | Qdrant horizontal sharding by org_id, HNSW index tuning |
| **Embedding computation bottleneck** | GPU inference, batch embedding, pre-computed embeddings for popular queries |
| **PostgreSQL connection exhaustion** | PgBouncer connection pooling, read replicas for search queries |
| **Celery worker scaling** | Autoscaling based on queue depth, separate queues for parse vs. embed vs. index |
| **Cross-encoder latency** | Batch reranking, async reranking with streaming, optional reranking toggle |
| **Cache invalidation** | Event-driven invalidation on document update/delete, TTL as fallback |
| **Multi-tenancy isolation** | Qdrant collection-per-org or payload filtering (trade: isolation vs. resource efficiency) |
